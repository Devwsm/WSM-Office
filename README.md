# WSM-Office (W.O.S 2.0) — Laravel

Sistem manajemen kantor internal Whisnu Santika Music (WSM). Hasil implementasi prototype `WOS_2_0_App_v32` (HTML/JS satu file) menjadi aplikasi Laravel multi-halaman. Sudah **live di production** (auto-deploy sejak 2026-09-23) dan dipakai karyawan untuk operasional, dengan prioritas **absensi** dan **work** (Work Tracker, kalender, rapat, memo).

**Stack:** Laravel 13.32 · PHP 8.3 (batas cPanel Rumahweb; `composer.json` mengunci platform ke 8.3.0) · MySQL · Tailwind CSS v4 + Vite · Alpine.js · Leaflet (peta geofence) · SweetAlert2 · `maatwebsite/excel` 4.0 · `barryvdh/laravel-dompdf` 3.1.

**Ukuran kode:** 28 model · 37 FormRequest · 53 migrasi · 5 seeder · 122 view Blade · 50 panduan halaman · 193 route (`php artisan route:list`) · **549 tes otomatis**.

**Legenda status:** ✅ ada & sesuai · ⚠️ ada tapi lebih sederhana / beda dari prototype · ❌ belum ada · ➕ tambahan (tidak ada di prototype)

## 1. Ringkasan sistem

**Fitur:** absensi (kantor, WFH, lapangan, gigs; geofence + selfie), pengajuan izin/cuti/lembur/koreksi presensi dengan approval, Work Tracker per project, Timeline Calendar, rapat (MoM), memo, KPI, kontrak, payroll, budget, royalti, legal, audit log, rekrutmen, serta pusat Export/Import. Ada 5 halaman publik (beranda, tentang, layanan, karir, kontak) dan form lamaran kerja.

**Hosting:** shared cPanel (Rumahweb) **tanpa terminal**. Akibatnya: tidak ada cron (rekonsiliasi absensi ikut trafik web lewat `AttendanceReconciler`), tidak bisa `artisan` di server, dan migrasi dijalankan lewat deploy-hook. Detail di **Bab 5**.

**Konvensi kode**

- Validasi utama lewat kelas `FormRequest` (`app/Http/Requests`). Endpoint kecil memakai `$request->validate()` langsung di controller: login, form kontak, penanda Absen, Dashboard Access, import, dan aksi Work Tracker/Kalender/sinkron sheet (edit satuan, section, drag tanggal).
- `/app` untuk semua akun internal; `/owner` untuk role `owner` dan `developer` (Dashboard Access khusus `owner`); `/manajer` untuk manajer/owner; `/dashboard` dijaga akses **modul**.
- Akses modul (`dashboard_access`, level `view`/`manage`) mengatur menu dan hak ubah di `/dashboard`, rekap, approval, dan rekrutmen. Ada 10 modul (sumber kebenaran: `DashboardAccess::MODULES`).
- `throttle` dipasang pada login (5/menit), form kontak dan lamaran (5/menit), absen, pengajuan, lembur, koreksi presensi, foto profil, balasan memo, buka kunci dashboard, blast memo, Kirim Reminder, import, sinkron sheet, reset password, Weekly Rhythm, drag tanggal kalender, edit satuan Work Tracker, dan deploy-hook Hook B.
- Audit log untuk aksi penting: karyawan, akses modul, approval, payroll (termasuk buka kembali), penanda Absen, pengaturan kantor, Beranda Publik, Kelompok Tim, import karyawan, reset password, Weekly Rhythm, drag tanggal kalender, visibility section, dan sinkron sheet. **Belum:** edit satuan Work Tracker, import KPI/Budget/Work Tracker, CRUD KPI dan Budget. Sudah: perubahan Project Budget dan akses kategori budget.

### Peran & akses

| Peran               | Area utama                                                                                                                                                                                                                                                                |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Publik / tamu       | Beranda, Tentang, Layanan, Karir + lamar, Kontak, Login                                                                                                                                                                                                                   |
| Semua akun internal | `/app/*` — absen, riwayat, pengajuan, lembur, koreksi, kalender tim, profil, memo/Inbox                                                                                                                                                                                   |
| Owner               | Semuanya: `/owner/*` + semua modul dashboard + boleh memutus semua approval                                                                                                                                                                                               |
| Developer           | Akses Tingkat 2: `/owner/*` **kecuali** Dashboard Access, lihat semua orang di Rekap Absensi, kelola karyawan non-Owner, reset password non-Owner, import/export karyawan. Modul dashboard-nya tetap dari akses yang diberikan Owner. **Tidak bisa** menyentuh akun Owner |
| Manajer             | Approval bawahan langsung, Tim Saya (`/manajer`), + modul yang diberikan Owner                                                                                                                                                                                            |
| HRD                 | Rekap absensi, rekrutmen, + modul yang diberikan Owner (sengaja tidak ikut approve izin/cuti)                                                                                                                                                                             |
| Karyawan            | `/app/*` + modul yang diberikan Owner (mis. Work Tracker `view`/`manage`)                                                                                                                                                                                                 |

**Role vs permission:** role (`owner`, `developer`, `manajer`, `hrd`, `karyawan`) adalah label jabatan yang menentukan area `/owner`, cakupan Rekap Absensi, dan akses Owner penuh. Permission adalah akses per modul (`none`/`view`/`manage`) yang menentukan menu dashboard dan boleh-tidaknya mengubah data. Role diatur di Karyawan → Edit; permission di Karyawan → Akses (hanya Owner). Akses modul adalah **data**, bukan hard-code: akun tanpa modul `work` mendapat 403 di Work Tracker, itu perilaku benar.

**Visibilitas project (kalender bersama karyawan):** `projects.visibility` bernilai `all` (default, semua karyawan), nama tim (`management`, `marketing`, `ga`, `creative`, `finance`, `legal`, `hr`), atau `assigned` (hanya Lead dan PIC). Project terlihat oleh: Owner dan Developer (selalu), Lead project itu, dan karyawan yang tim kerjanya cocok. Task tetap terlihat oleh PIC-nya (PIC 1, PIC 2/3, atau namanya tertulis di catatan teks lama `additional_pic`) walau projectnya dibatasi, dan task tanpa project selalu terlihat. `users.work_team` kosong ditebak dari divisi + jabatan (`User::workTeam()`); Owner selalu Management, tebakan gagal = `other`. Aturan ini hanya berlaku di `/app/kalender-tim` (task, dropdown Project, dan dropdown PIC). **Tidak** berlaku untuk halaman dashboard modul Work (Work Tracker, Projects, Timeline Calendar, Rapat), Team Overview manajer, dan export, yang memang untuk pengelola.

**PIC lebih dari satu orang per task:** `work_items.pic_employee_id` tetap PIC 1 (utama); PIC 2 & PIC 3 disimpan di tabel `work_item_additional_pics` (relasi ke `users`, maksimal 2). Definisi "task milik seseorang" hanya ada di satu tempat, `WorkItem::scopeForPic()`, dipakai Home karyawan, kalender (dua versi), filter PIC board, dan Team Overview (task bersama dihitung untuk tiap anggota tim yang terlibat). Kolom teks `additional_pic` tidak dihapus: tetap dipakai penanda ALL TEAM dari action item MoM dan catatan pihak luar; teksnya otomatis dikosongkan saat task diberi PIC tambahan sungguhan. Migrasi `2026_09_30_091136_work_item_additional_pics` memindahkan nama di `additional_pic` yang cocok persis dengan satu user jadi PIC tambahan (nama yang tidak persis dibiarkan sebagai teks). Belum ada: PIC 2/3 lewat Import Work Tracker (kolom `pic` masih satu orang) dan lewat action item MoM.

**Section per project bisa diatur:** `work_items.section` tetap teks bebas (import/export, MoM, reminder, dan kalender tidak berubah). Pengaturan tampilannya ada di tabel `project_sections` (`project_id`, `name`, `color` nullable, `sort_order`; unik per project + nama). `color` kosong = warna default dari nama (`ProjectSection::defaultColorFor`, sama persis dengan warna sebelum fitur ini). Warna dan urutan berlaku **per project**, bukan global antar project. Baris section dibuat otomatis oleh hook `WorkItem::saved` (semua jalur tulis ikut) dan ditambal `ProjectSection::syncMissing()` saat board dibuka; section tanpa baris tetap tampil, hanya tanpa tombol atur. Migrasi `2026_09_30_134258_project_sections` mengisi baris dari item yang sudah ada dengan urutan = item pertama tiap section, jadi tidak ada yang bergeser. Hapus section berisi item ikut menghapus item-nya (nama section harus diketik persis). Tombol geser dan hapus disembunyikan saat filter PIC/Progress aktif. Belum ada: ganti nama section, geser lewat drag-and-drop, dan pengaturan section untuk task tanpa project.

**Persetujuan izin/cuti/lembur/koreksi:** halaman persetujuan butuh akses modul `people`, tetapi yang boleh memutuskan adalah **atasan langsung** karyawan itu; Owner boleh memutus semuanya (Developer hanya untuk bawahan langsungnya). Rekap Absensi manajer mencakup dirinya dan seluruh bawahan turunannya (`User::visibleAttendanceUserIds()`, dipakai bersama oleh halaman Rekap, Export, dan Team Overview).

**Aturan akun Owner dan Developer** (dijaga di controller dan FormRequest, bukan hanya disembunyikan di tampilan):

- Developer boleh membuat, mengubah, menonaktifkan, dan mengaktifkan kembali akun apa pun **kecuali Owner**, dan hanya bisa memilih role Karyawan, Manajer, atau HRD. Akun Owner dan Developer baru hanya bisa dibuat Owner (lewat form maupun import).
- Reset password (dashboard IT, Manage `it`): akun sendiri tidak bisa direset; akun Owner hanya oleh Owner; akun Developer hanya oleh Owner atau Developer lain.
- Password sementara hasil reset tampil satu kali, tidak masuk audit log, dan semua sesi lama akun itu dikeluarkan. Akun ditandai `must_change_password`: sebelum diganti, semua halaman selain Profil dan logout dialihkan ke Profil. Tanda yang sama dipasang pada akun hasil import dengan password kosong (default `password`).

**Akun & seeder**

- `DatabaseSeeder` hanya memanggil `OfficeSettingSeeder` dan `ProductionSeeder` (akun asli). `migrate:fresh --seed` di lokal membuat akun asli, bukan data demo.
- Data demo lokal: `php artisan db:seed --class=DemoSeeder`, lalu bila perlu `--class=TestingAccountsSeeder` (Ancha `ancha@wsm.test` = manajer dengan Manage 10 modul; Arga `arga@wsm.test` = developer; password keduanya `password`). Jangan dijalankan di production.
- Detail seeder production dan peringatannya di **5.5**.

## 5. Production (deploy & operasional)

Semua hal tentang server production ada di bab ini. Isinya dicocokkan dengan `.github/workflows/deploy.yml` dan kode. Hal yang hanya ada di server dan tidak bisa dicek dari repo ditandai **(server)**.

### 5.1 Alur deploy

```
push ke main
  → GitHub Actions (.github/workflows/deploy.yml, job "deploy", ±45–60 detik)
      1. checkout
      2. PHP 8.3 + composer install --no-dev   (hanya validasi composer.json; vendor TIDAK diupload)
      3. Node 20 + npm ci + npm run build
      4. FTPS: kode aplikasi → ~/wsm-office                      (secret FTP_APP_DIR)
      5. FTPS: public/build  → ~/public_html/<domain>/build      (secret FTP_PUBLIC_DIR)
      6. curl https://<APP_URL>/deploy-hook.php?token=…          → migrate --force + config/route/view cache
```

- **Server:** shared cPanel Rumahweb, tanpa SSH. Domain `wos.whisnusantika.com`; document root `~/public_html/wos.whisnusantika.com`; project di `~/wsm-office` (di luar `public_html`).
- **Upload:** `SamKirkland/FTP-Deploy-Action@v4.3.5`, `protocol: ftps`. Sinkronisasi memakai `.ftp-deploy-sync-state.json` di folder tujuan **(server)**: hanya file yang berubah yang dikirim, dan file yang dihapus dari repo ikut terhapus di server. Jangan hapus file state itu; kalau hilang, semua file diupload ulang (lama).
- **Retry otomatis:** dua step upload FTP masing-masing punya step retry, karena `Error: Timeout (control socket)` adalah bug flaky yang dikenal di `FTP-Deploy-Action`.
- **Exclude upload kode:** `.git*`, `node_modules`, `tests`, `storage`, `public`, `vendor`, `.env`, `.env.example`, `AGENTS.md`, `CLAUDE.md`, `README.md`, `phpunit.xml`, `package.json`, `package-lock.json`, `vite.config.js`, `.editorconfig`, `.npmrc`. Folder `docs/` ikut terupload.
- ⚠️ **Tidak ada tes di pipeline.** Job hanya `deploy` tanpa `needs`, jadi push dengan tes merah **tetap ter-deploy**. Jalankan `php artisan test` sebelum push (5.9). Perbaikan yang disarankan: tambah job `test` dan pasang `needs: test` pada job `deploy` (butuh `composer install` dengan dependency dev).

### 5.2 Otomatis vs manual

| Yang berubah                                                                                    | Ikut deploy? | Kalau perlu diubah                                                                                                                                |
| ----------------------------------------------------------------------------------------------- | ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| Kode aplikasi (`app/`, `config/`, `routes/`, `resources/`, `database/`, `bootstrap/`, composer) | ✅           | Push ke `main`                                                                                                                                    |
| Aset build (`public/build`)                                                                     | ✅           | Push (build otomatis)                                                                                                                             |
| Migrasi baru, cache config/route/view                                                           | ✅ via hook  | Push                                                                                                                                              |
| `vendor/`                                                                                       | ❌           | Upload manual (zip → File Manager → Extract) **setiap `composer.json`/`composer.lock` berubah**. Kalau lupa, kode yang butuh paket baru error 500 |
| File `public/` selain `build/` (`index.php`, `.htaccess`, `robots.txt`, `favicon.ico`, statis)  | ❌           | Upload manual ke `~/public_html/<domain>/`. Setelah mengubah `index.php` server, perbarui juga `docs/server/index.php`                            |
| `.env` dan `storage/`                                                                           | ❌           | Edit manual di server. Perubahan `.env` baru berlaku setelah hook jalan lagi (5.6)                                                                |

### 5.3 GitHub Secrets

Settings → Secrets and variables → Actions → Repository secrets. Jangan menulis nilai secret di repo, README, atau chat.

| Secret                         | Isi                                           | Catatan                                                                                                          |
| ------------------------------ | --------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| `FTP_HOST`                     | **Alamat IPv4 server FTP** (bukan hostname)   | Sengaja IP untuk menghindari bug pemilihan IPv4/IPv6 Node. Kalau server pindah, ambil A record baru (`nslookup`) |
| `FTP_USERNAME`, `FTP_PASSWORD` | Akun FTP cPanel khusus deploy                 | Berakar di home cPanel. Kalau password diganti, ganti di cPanel dulu, lalu di secret                             |

| `APP_URL`                      | Domain saja, **tanpa** `https://`             | Workflow menyusun `https://${APP_URL}/deploy-hook.php`                                                           |
| `DEPLOY_TOKEN`                 | Token acak panjang                            | Harus sama persis dengan `$expectedToken` di `deploy-hook.php` **(server)**                                      |

### 5.4 Deploy hook

Ada dua mekanisme; hanya A yang dipakai.

**A. `deploy-hook.php` mandiri (dipakai workflow).** Ada di `~/public_html/<domain>/deploy-hook.php` **(server)**, tidak ada di repo. Dipanggil `GET ?token=…`. Jika token cocok: memuat `vendor/autoload.php` + `bootstrap/app.php` dari `~/wsm-office`, lalu `migrate --force`, `config:cache`, `route:cache`, `view:cache`. Balasan `DEPLOY SELESAI`; exception → HTTP 500 `ERROR: …`; token salah → 403.

<details>
<summary>Isi file (token dikosongkan; simpan salinannya di luar server)</summary>

```php
<?php
// deploy-hook.php — taruh di public_html/<domain>/deploy-hook.php
// Di-trigger via HTTP oleh GitHub Actions setelah upload selesai.
$expectedToken = ''; // isi string acak panjang, SAMA dengan secret DEPLOY_TOKEN

// Token kosong harus ditolak: hash_equals('', '') bernilai true.
if ($expectedToken === '' || !hash_equals($expectedToken, $_GET['token'] ?? '')) {
    http_response_code(403);
    exit('Forbidden');
}

$appPath = __DIR__ . '/../../wsm-office'; // sesuaikan kalau lokasi berbeda

require $appPath . '/vendor/autoload.php';

$app = require_once $appPath . '/bootstrap/app.php';
$kernel = $app->make(Illuminate\Contracts\Console\Kernel::class);

header('Content-Type: text/plain');

try {
    $kernel->call('migrate', ['--force' => true]);
    echo "migrate: OK\n" . $kernel->output();

    $kernel->call('config:cache');
    echo "config:cache: OK\n";

    $kernel->call('route:cache');
    echo "route:cache: OK\n";

    $kernel->call('view:cache');
    echo "view:cache: OK\n";

    echo "DEPLOY SELESAI\n";
} catch (\Throwable $e) {
    http_response_code(500);
    echo "ERROR: " . $e->getMessage() . "\n";
}
```

</details>

**B. `POST /system/deploy-hook` di dalam aplikasi (tidak dipakai).** `DeployHookController` + route `system.deploy-hook`, peninggalan pipeline pertama. Token lewat header `X-Deploy-Token`, dibandingkan (`hash_equals`) dengan `DEPLOY_HOOK_TOKEN` di `.env` (`config/services.php` → `deploy_hook.token`); throttle 5/menit; dikecualikan dari CSRF; selain tiga cache di atas juga menjalankan `event:cache`. Selama `DEPLOY_HOOK_TOKEN` kosong, route ini selalu 403, jadi aman dibiarkan.

**Catatan hook A**

- Token ada di URL, jadi tercatat di access log server. Hook B (header) lebih rapi kalau suatu saat dipindah.
- `curl -sf` di workflow menyembunyikan isi balasan. Untuk melihat pesan error, panggil manual: `curl -i "https://<domain>/deploy-hook.php?token=…"`.
- Karena ada `config:cache`, lihat 5.6.

### 5.5 Database dan seeder

- **Migrasi** jalan otomatis tiap deploy lewat hook (`migrate --force`). Hanya maju; tidak ada rollback otomatis.
- **Seeder tidak dijalankan pipeline.** `DatabaseSeeder` hanya memanggil `OfficeSettingSeeder` dan `ProductionSeeder`.
- **`ProductionSeeder`** membuat 11 akun asli (Owner Ancha, Developer Arga dengan Manage semua modul, dan 9 karyawan dengan role default `karyawan` dan atasan Owner; nama "WSM ..." adalah label kontak, belum tentu nama asli), plus memo pinned "Welcome WSM v1". Semua akun memakai satu password sementara (konstanta `TEMP_PASSWORD` di seeder) dengan `must_change_password = true`.
- ⚠️ **Jalankan sekali saja.** Kedua seeder memakai `updateOrCreate` dengan nilai tetap: menjalankan ulang `ProductionSeeder` mengembalikan password semua 11 akun ke password sementara dan menimpa nama, role, divisi, jabatan, dan atasan; menjalankan ulang `OfficeSettingSeeder` menimpa pengaturan kantor yang sudah diubah Owner.
- ⚠️ **Password sementara tertulis di repo** (dan di riwayat git). Siapa pun yang punya akses repo bisa mengambil alih akun yang belum pernah login. Pastikan tidak ada akun yang masih `must_change_password = true` lebih lama dari perlu, dan jangan jalankan seeder lagi sebelum `TEMP_PASSWORD` diganti.
- **Status di production: tidak bisa diverifikasi dari repo.** Cek manual: `[ ]` `OfficeSettingSeeder` sudah dijalankan · `[ ]` `ProductionSeeder` sudah dijalankan.
- **Cara menjalankan tanpa SSH** (hanya pertama kali): (a) impor SQL — di lokal dengan database kosong `php artisan migrate:fresh --seed`, ekspor lewat phpMyAdmin, impor ke server yang masih kosong; atau (b) hook sekali pakai — tambahkan blok di bawah ke `deploy-hook.php` setelah blok `migrate`, buka sekali dengan `&seed=1`, lalu **hapus blok itu lagi**. Jangan pernah menaruh `seed=1` di workflow.

```php
if (($_GET['seed'] ?? '') === '1') {
    $kernel->call('db:seed', ['--class' => 'ProductionSeeder', '--force' => true]);
    echo "db:seed: OK\n" . $kernel->output();
}
```

- **Jangan** menjalankan `migrate:fresh`/`migrate:refresh`/`db:wipe`, `db:seed` tanpa `--class`, `DemoSeeder`, atau `TestingAccountsSeeder` di production.

| `WOS_PREVIEW_MODE`         | `false` saat dipakai operasional        | Mematikan Peringatan preview     |
| `LOG_LEVEL`, `LOG_CHANNEL` | `warning`, `daily`                      | Log tidak membengkak             |
| `DEPLOY_HOOK_TOKEN`        | Hanya kalau memakai Hook B (5.4)        | Kosong = route Hook B selalu 403 |

- **Perubahan `.env` baru berlaku setelah hook jalan lagi**, karena `config:cache` membekukan nilainya. Pemicu: push commit apa pun (`git commit --allow-empty -m "trigger deploy"`), buka URL hook, atau hapus `~/wsm-office/bootstrap/cache/config.php`.
- **Status `.env` produksi final: belum terverifikasi dari repo (server).**
- **Popup informasi preview:** `config/entry_popups.php` + `App\Support\EntryPopups` + `resources/js/entry-popups.js`. Saklar `.env`: `WOS_PREVIEW_MODE` (default `true`) mematikan Peringatan preview di semua pintu; `WOS_ENTRY_POPUPS` (default `true`) mematikan semua popup. Popup ditandai di `sessionStorage`; naikkan `version` di config supaya muncul lagi setelah teks diubah. Tidak muncul di halaman error, layar Kunci Dashboard, dan selama akun wajib ganti password.

### 5.7 Aset Vite

Browser tidak memakai CSS Tailwind dan JavaScript Alpine apa adanya; Vite merakitnya menjadi file jadi di `public/build/`. Server tanpa terminal tidak bisa menjalankan Vite, jadi rakitannya dibuat GitHub Actions (`npm run build`) lalu di-upload otomatis ke `public_html/<domain>/build`.

- `public/hot` (penanda dev-server Vite) **tidak boleh** ada di server: kalau ada, Laravel mencari CSS/JS ke localhost dan halaman tampil tanpa gaya. `public/hot` dan `public/fonts-manifest.dev.json` di-`.gitignore` dan tidak ikut pipeline.
- `public/index.php` di server **wajib** memanggil `$app->usePublicPath(__DIR__)` agar `@vite` membaca manifest dari `public_html/<domain>/build`, bukan dari `~/wsm-office/public/build`. Salinan yang benar ada di `docs/server/index.php`.
- Setelah mengubah class Tailwind di view, tampilan production baru berubah lewat build ulang (otomatis di Actions).

### 5.9 Kalau deploy gagal, dan aturan rutin

| Gejala di GitHub Actions                                          | Tindakan                                                                                                                                                                                                                                                       |
| ----------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Upload gagal `Timeout (control socket)` ±2 detik, run tetap hijau | Tidak perlu tindakan; step retry yang menyelamatkan                                                                                                                                                                                                            |
| Upload gagal di percobaan 1 **dan** retry, run merah              | Pastikan `FTP_HOST` berisi IPv4. Re-run **run terbaru** sekali lagi. Kalau ±30 detik: tes dari lokal `Test-NetConnection <ip> -Port 21`, cek `nslookup` (IP berubah?); kalau lokal berhasil tapi runner gagal, hubungi Rumahweb                                |
| Upload gagal `530 Login incorrect`                                | Cek `FTP_USERNAME`/`FTP_PASSWORD` dan password akun FTP di cPanel                                                                                                                                                                                              |
| Hook gagal `curl` exit 22 (tanpa pesan)                           | Panggil manual `curl -i "https://<domain>/deploy-hook.php?token=…"`. 403 = token beda dengan `DEPLOY_TOKEN`; 500 = baca pesan `ERROR:` (migrasi gagal, `vendor/` tidak cocok)                                                                                  |
| Hook gagal `curl` exit 60                                         | Sertifikat SSL tidak terverifikasi; cek AutoSSL                                                                                                                                                                                                                |
| Situs 500 setelah deploy hijau                                    | Biasanya `vendor/` tidak cocok dengan `composer.lock`: upload ulang `vendor/` (5.2), cek `storage/logs/laravel.log` di server                                                                                                                                  |
| Deploy hijau tapi tampilan production beda dari lokal (CSS lama)  | Bandingkan (1) `<link>` CSS di page source (Ctrl+U), (2) `https://<domain>/build/manifest.json`, (3) isi file CSS. Kalau (1) ≠ (2): pastikan `index.php` server memanggil `usePublicPath(__DIR__)` dan tidak ada manifest lama di `~/wsm-office/public/build/` |

**Aturan rutin**

- **Tes hijau sebelum push:** `php artisan test` (pipeline tidak menjalankannya). Urutan lengkap ada di **5.12 Checklist rilis**.
- **Jangan re-run run lama.** Re-run memakai commit lama dan menyinkronkan server ke isi commit itu, sehingga bisa menimpa deploy yang lebih baru. Re-run hanya run **terbaru**, atau push commit baru. Run yang gagal di step pertama tidak mengubah apa pun di server.
- **Cek run hijau** setelah tiap push: upload kode, upload build, dan trigger hook. Untuk perubahan tampilan, cocokkan nama CSS di page source dengan `manifest.json`.
- **Jangan** `migrate:fresh` di production, jangan menjalankan seeder ulang (5.5), jangan menghapus `.ftp-deploy-sync-state.json`, jangan edit kode langsung di server.
- **Rollback:** tidak ada mekanisme otomatis. Revert commit lalu push; migrasi tidak ikut mundur, jadi migrasi yang merusak dibetulkan dengan migrasi baru.

### 5.12 Checklist rilis (sebelum push → auto deploy)

Pipeline tidak menjalankan tes dan tidak bisa di-rollback otomatis (5.1, 5.9), jadi urutan ini dijalankan manual **sebelum** `git push` ke branch yang memicu deploy.

**A. Di lokal**

1. `git pull` dulu, pastikan branch bersih dan sama dengan `origin` (jangan menimpa commit orang lain).
2. Terapkan perubahan (`git apply --whitespace=nowarn <file>.patch` atau salin file), lalu `git status` dan cek hanya file yang dimaksud yang berubah. **Cek `git diff` setelah menyimpan file Blade**: pemformat otomatis editor pernah memecah tag dan teks (mis. `+2 item` terpotong, `<button type=` jadi `<buttontype=`) tanpa diminta.
3. `php artisan migrate` di database **lokal** (bukan production), buka halaman yang berubah, lalu `php artisan test` harus hijau semua.
4. `npm run build` kalau ada perubahan CSS/JS Vite. Perubahan Blade murni tidak butuh ini.
5. Uji manual di browser (tes otomatis tidak menyentuh UI): desktop dan HP, akun Owner dan akun View-only.
6. Kalau ada migrasi baru: baca isinya. Harus **nullable/default, tidak menghapus atau mengganti nama kolom/tabel lama** (5.11).

**B. Sebelum push**

7. **Backup database** lewat cPanel (Backup atau phpMyAdmin Export), simpan di luar server. Wajib kalau ada migrasi baru.
8. Pilih jam sepi (bukan sekitar jam masuk dan pulang), karena upload FTP tidak atomik (5.11).
9. Untuk perubahan alur harian karyawan, siapkan memo pengumuman.
10. Commit dengan pesan per fitur, lalu `git push`.

**C. Sesudah push**

11. Buka GitHub Actions: tiga langkah (upload kode, upload build, trigger hook) harus hijau. Jangan re-run run lama (5.9).
12. Cek balasan hook berisi `DEPLOY SELESAI` dan `migrate: OK`. Kalau 500 `ERROR:`, baca pesannya (5.9).
13. Buka halaman login, absen, dan halaman yang baru diubah di production. Kalau ada yang rusak: revert commit lalu push.
14. Catat perubahan di **System Change Log** (Dashboard IT) dan umumkan ke tim.
